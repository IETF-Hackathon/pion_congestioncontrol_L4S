01 · What problem

Keep interactive media responsive under load

When a bottleneck fills, queuing can add delay and delay variation to a WebRTC stream. This POC asks whether Prague with L4S signaling improves those outcomes while preserving useful throughput.

A complete Pion experiment needs the sender’s congestion controller, receiver feedback, and the bottleneck queue to work together. The proposed path combines UDP-Prague, RFC 8888 feedback, outer-IP ECN handling in ICE/UDP, and a DualPI2 router.

The comparison uses the same media source and bottleneck for GCC and Prague. It will measure performance and confirm that CE marks reach the controller through receiver feedback.

02 · Existing and optional congestion control

Pion’s default feedback and optional GCC

Separate feedback plumbing from the algorithm that actually changes a sender’s bitrate. Pion’s default feedback support is not itself a congestion controller.

01

Default Pion: TWCC feedback

The default interceptor setup generates transport-wide congestion-control (TWCC) feedback for received media when negotiated. This gives the remote sender information about packet delivery. The application must separately configure its local sender’s rate estimation, packet tracking, pacing, and encoder adaptation. RFC 8888 feedback can also be configured separately.

Performance meaning: feedback is available, but local rate-control performance depends on the controller and pacer the application uses.

02

Optional Pion GCC

pion/interceptor provides an optional Google Congestion Control implementation, including bandwidth-estimation and pacing components. It must be explicitly wired into the application; it is not installed as the default Pion sender controller.

Performance meaning: GCC estimates a target rate from transport feedback and can pace packets. Pion’s BWE test runner provides RFC 8867-style interactive-media scenarios. Actual delay, loss, and throughput depend on the path, configuration, pacer, and media source; this POC has no testbed GCC performance measurements yet. The run preview contains the completed local transport checks.

Code references: Pion default interceptor registration and optional GCC estimator and pacer.

Performance hypothesis: Prague with working L4S signaling may reduce queue delay, RTT variation, and loss while maintaining goodput compared with the configured GCC baseline. The experiment must establish whether this holds; no numerical improvement is assumed.
03 · System design

Connect the controller to the network signals

Prague controls the sender. DualPI2 manages the bottleneck queues. Pion carries RTP and returns congestion feedback. The test is valid only when ECN marking survives the full ICE/UDP path.

Critical integration boundary: RTP interceptors can process RTP/RTCP, but ECT(1) marking and CE observation happen on the outer IP packet in the ICE/UDP transport.

What changes when UDP-Prague is carried by Pion?

The congestion-control roles match, but the example protocols do not. UDP-Prague's standalone sender and receiver exchange custom UDP data/ACK messages. WebRTC endpoints exchange RTP media and RTCP feedback over ICE/UDP, so the Prague algorithm needs an adapter at the WebRTC boundary.

03a · Prague feedback loop

Turn ECN markings into pacing and rate changes

Prague treats ECN as a measured congestion level, not as an instruction to halve the rate for every marked packet. Accurate receiver feedback closes the loop between the L4S bottleneck and the sender.

Prague sender             DualPI2 / L4S queue             Pion receiver
ECT(1) packet  ─────────► selected packets become CE ───► observe outer-IP CE
      ◄──────── RFC 8888 feedback: received / CE / lost ────────────────┘
update window, pacing rate, burst allowance, and media target

The sender marks outgoing outer IP packets ECT(1). When its shallow L4S queue begins to build, DualPI2 changes selected packets from ECT(1) to CE (Congestion Experienced) instead of waiting for packet loss. The receiver must read the ECN field from each received ICE/UDP packet, associate it with the corresponding RTP packet, and return sufficiently accurate congestion feedback.

For RTP over UDP, both endpoints signal ECN support and use RTCP RFC 8888 congestion-control feedback. Reporting only that “some congestion occurred” is insufficient: Prague needs the extent of CE marking so its response scales with the amount of congestion.

1

Measure the marked fraction

From newly reported traffic, calculate the proportion marked CE:

mark fraction = CE-marked traffic
                ─────────────────
                acknowledged traffic

Implementations must handle cumulative counters, duplicates, reordering, loss, and counter wrap without counting a packet twice.

2

Smooth the signal

Prague maintains a moving estimate conventionally called alpha:

alpha = (1 − g) × old alpha
        + g × mark fraction

This filters individual marks while retaining the current level of persistent congestion.

3

Reduce proportionally

On CE feedback, Prague reduces its congestion window approximately as:

new window = old window
             × (1 − alpha/2)

The controller normally makes no more than one ECN-driven reduction per RTT, while continuing to update its congestion estimate.

Example: if the smoothed marking level is 10%, Prague reduces the window by about 5%. Sparse marking causes a gentle response; persistent marking causes a stronger response. This fine-grained reaction is what allows Prague to keep the L4S queue shallow without repeatedly applying a classic 50% backoff.

How the controller output reaches WebRTC

After processing feedback, UDP-Prague exposes a pacing rate, packet window, permitted burst size, and packet size. A real-time integration can also derive a source or next-frame budget. The Pion adapter must apply these outputs to the RTP pacer and rate-controllable media source while ensuring GCC is not controlling the same stream.

Packet loss remains a separate, stronger safety signal with Reno- or CUBIC-compatible behavior. If the receiver detects ECN bleaching or invalid ECN behavior, it reports an L4S error so the sender can stop relying on ECT(1) and fall back safely.

What is still missing here

The experimental Prague mode now marks SRTP data ECT(1), reads socket ECN metadata, returns ECN-aware RFC 8888 reports, and feeds the pinned PragueCC core. A synchronous pacer applies its rate and byte-window outputs. Local checks pass; physical DualPI2 validation, adaptive media encoding and complete experiment metrics remain pending.

Technical references: RFC 9331 L4S ECN requirements, the Prague congestion-control specification, and the UDP-Prague reference implementation.

04 · Hackathon plan

Build it in testable layers

Start with interoperable feedback and a repeatable media stream. Add Prague and transport ECN support as separate milestones so failures are diagnosable.

1

Baseline Pion WebRTC application

Fork the Pion examples or create a companion repo. Add two Pion endpoints, simple signaling, and a repeatable RTP video source and sink.

2

Negotiate and log RFC 8888 feedback

Enable Pion congestion-control feedback and verify the remote endpoint sends reports with usable per-packet delivery and ECN information.

Explicitly configure GCC as the baseline and validate negotiation, feedback cadence, and report parsing before switching to Prague.

3

Integrate Prague and pacing

Wrap PragueCC with cgo or port it to Go. Feed its feedback state and use its rate/window outputs to drive the RTP pacer and encoder target. Remove or disable competing GCC control for this stream.

4

Add outer-IP ECN support

Mark outbound ICE/UDP packets ECT(1), read incoming CE marks, and connect those observations to the RFC 8888 feedback path. Confirm the marks survive the exact OS, ICE, SRTP, and network path used in the demo.

5

Run the DualPI2 interop matrix

Place a bandwidth-limited DualPI2 bottleneck between endpoints. Test Prague alone, Prague with a classic flow, and negative cases such as ECN bleaching or a non-L4S queue.

08 · What I learned

Lessons from the design work

These are findings from defining the integration. Experimental lessons can be added after implementation and interop runs.

  • The work crosses layers. RTP interceptors handle media and RTCP; ECN marking and observation occur on the outer IP packet in ICE/UDP.
  • Feedback needs an active controller. TWCC reporting alone does not adapt the local Pion sender. Both GCC and Prague need to be explicitly connected to sending behavior.
  • Transport standards have distinct roles. RFC 9768 defines TCP AccECN. This WebRTC endpoint uses RTP feedback under RFC 8888; QUIC has its own ECN feedback.
  • Performance needs correlated evidence. Captures, CE reports, rate changes, and queue measurements should explain the observed latency and throughput.
